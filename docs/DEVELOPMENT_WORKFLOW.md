# Рабочий процесс разработки на двух компьютерах

## Источник истины

GitHub — общий удалённый источник кода. Ветка `feature/shared-integration-settings` на дату документации указывает на commit `bd5ea965cc5e4431dc22222e26b4c2ab448dd437`. Она на 132 коммита опережает `main` и не отстаёт от него. Это означает, что ветка содержит существенный набор изменений, ещё не включённых в `main`.

Не считайте локальные папки двух компьютеров автоматически синхронизированными: GitHub содержит только отправленные коммиты. Незакоммиченные и неотправленные изменения остаются на соответствующем компьютере.

## Правило работы

Не работайте одновременно в одной ветке на двух компьютерах. Выберите один компьютер как активный, завершите там задачу, протестируйте, закоммитьте и отправьте изменения. Только после этого переходите ко второму компьютеру и забирайте новые коммиты.

## Перед началом работы на любом компьютере

Откройте PowerShell в каталоге репозитория:

```powershell
git status --short
git branch --show-current
git log -1 --oneline --decorate
git fetch origin
git status -sb
```

Если `git status --short` показывает изменения, **не выполняйте pull, switch, reset или clean**. Сначала определите, какие файлы изменены и нужны ли эти изменения. Сохраните их отдельным коммитом или сделайте проверенную резервную копию. Не используйте `git add .`: добавляйте только конкретные проверенные файлы.

## Подключение второго компьютера к существующей рабочей ветке

Если на втором ПК уже есть клон репозитория и рабочее дерево чистое:

```powershell
git fetch origin
git switch --track origin/feature/shared-integration-settings
```

Если локальная ветка с таким именем уже существует:

```powershell
git switch feature/shared-integration-settings
git status -sb
```

После проверки чистого состояния и только если локальная ветка действительно должна следовать за удалённой:

```powershell
git pull --ff-only origin feature/shared-integration-settings
```

Если ветка не fast-forward или Git сообщает о расхождении — остановитесь и разберите граф коммитов. Не применяйте принудительное обновление.

## Передача работы с первого ПК на второй

На первом ПК после тестов:

```powershell
git status --short
git diff --check
git diff
```

Добавьте только нужные файлы, создайте коммит и отправьте:

```powershell
git add <проверенные-файлы>
git commit -m "Краткое описание изменения"
git push origin feature/shared-integration-settings
```

На втором ПК:

```powershell
git status --short
git fetch origin
git log --oneline HEAD..origin/feature/shared-integration-settings
```

Если локальное дерево чистое и список коммитов ожидаемый:

```powershell
git pull --ff-only origin feature/shared-integration-settings
```

## Если на компьютерах разные локальные изменения

Не объединяйте их механически. На каждом компьютере выполните:

```powershell
git status --short
git branch --show-current
git log -5 --oneline --decorate
git diff --stat
git diff --cached --stat
```

Сохраните вывод и отдельно выясните, какие изменения уже есть в коммитах, какие не закоммичены, а какие не отправлены. Только после этого выбирайте порядок переноса. Не перезаписывайте одну рабочую копию содержимым другой.

## Что не синхронизируется через Git

Обычно не должны попадать в репозиторий:

- `venv/`, `.venv/` и другие виртуальные окружения;
- `__pycache__/`, `.pytest_cache/`;
- `build/`, `dist/` и собранные EXE/MSIX;
- локальные пользовательские настройки и секреты;
- временные архивы, логи и тестовые артефакты.

Пользовательские настройки приложения должны храниться отдельно от исходного кода и не переноситься между ПК через коммиты, если только это не специально подготовленный пример конфигурации.
